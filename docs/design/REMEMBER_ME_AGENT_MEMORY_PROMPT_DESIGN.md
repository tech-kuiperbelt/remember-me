# Remember Me — Agent 长期记忆提示词设计

> **版本：V2 · 讨论定稿**  
> **日期：2026-10-15**  
> **用途**：记录 AGENTS.md / CLAUDE.md 等项目指令中的 Remember Me 使用规则，以及规则背后的设计依据。供今后持续评审、调整和版本迭代。  
> **范围**：Agent 使用记忆的行为规范；不是 MCP 工具 API 文档，也不是 Remember Me 服务端 Schema 设计。

---

## 1. 产品定位与总目标

Remember Me 是供 LLM Agent 使用的长期记忆服务；Web UI 主要供用户查看、理解、整理和管理这些记忆。日常记忆的检索、积累、使用应主要发生在 Agent 的工作过程中，而不是要求用户手工维护一套知识库。

**核心目标：让 Agent 在思考中自然回忆，在工作中主动积累，从经历中提炼知识，并随着新事实不断修正已有记忆。**

这里的“像人一样回忆”是对**期望行为**的类比：提示词引导模型决定何时调用记忆工具，并不保证模型具备人类式记忆或每次都能正确触发检索。

设计追求：

- **主动但不机械**：回忆发生在需要的时候，而不是每个任务开头固定调用一次。
- **先回忆、少重复探索**：当需要重新寻找做法时，先考虑是否已有经验。
- **重质量、轻流水账**：保存未来有价值的知识，不把所有对话都复制进数据库。
- **用户掌控**：记忆是历史参考；当前事实和用户明确指令优先。影响未来行为的自拟规则须先征求用户同意。
- **长期指令要精简**：行为原则写在项目指令文件，API 参数和传输细节交给 MCP 工具说明与 `/read-me`。

## 2. 整体结构（后续讨论沿用此框架）

| 模块 | 主要问题 | 已确定的方向 |
| --- | --- | --- |
| **Recall — 读取** | 什么时候回忆？如何找？ | 情境、方法、决策、行动四类检索意图；必要时迭代；足够时停止 |
| **Remember — 写入** | 什么值得记？何时写？ | 用户明确要求、信息长期价值、阶段回顾三类触发 |
| **Abstraction — 提炼** | 记什么层次？ | 事件、知识、原则可独立存在，可抽象并相互引用 |
| **Deduplication — 演进** | 新增还是更新？ | 写入前查重；保留独立事件，合并重复知识，修正过时结论 |
| **Organization — 组织** | 怎样便于以后查找？ | Namespace、Categories、Keywords、Anchors 分工明确 |
| **Report — 反馈** | 怎么知道记忆是否有用？ | 实际阅读、使用或评估后，基于真实贡献主动反馈 |
| **Safety — 边界** | 如何避免误用？ | 保护秘密；尊重当前指令；重要冲突说明；破坏性操作需授权 |

### 2.1 Recall：让记忆贯穿思考，而不是流程开始时的仪式

四种意图不是四种不同的 MCP 工具，也不是每个任务都必须依次执行的步骤：

1. **Contextual Recall（情境回忆）**：分析问题时，联想到过去是否有类似事件、背景、经验；信息不足时调整查询线索并再次检索。
2. **Procedural Recall（方法回忆）**：在探索项目环境、寻找工具/配置/数据库查询方式或反复试错**之前**，先检索已有做法，避免重复摸索。
3. **Decision Recall（决策回忆）**：重要方案或决定形成前，主动检查历史决策、约束、风险、失败教训和已作承诺。
4. **Action Recall（行动回忆）**：准备执行提交、部署、删除等关键操作前，查看是否存在适用的长期行动规则（如 `action-rule`）。即便已知道如何操作，也应留意既有规则。

检索应具有**迭代性**：首次没有找到，不一定代表记忆不存在；应根据新线索调整关键词、检索方式或范围，必要时读取原文。但若已经有可靠的下一步做法，或继续查找明显没有价值，应停止，避免无意义调用。

**实际例子：本地数据库查询**

- 用户让 Agent 查询本地数据库。
- 不理想的行为：直接从寻找连接方式、翻配置文件、试各种工具开始；用户不得不打断并提醒“先查记忆”。
- 期望的行为：如果需要重新探索连接方法，先检索“本地数据库 / 连接 / 查询步骤”等历史方法，确认仍适用后复用；没有可用记忆再探索。
- **例外**：下一步已经有明确且可靠的执行办法时，无须为了形式再搜索一次；但关键操作的 Action Rule 检查另行考虑。

**记忆不是命令，也不是事实权威**：遇到与现状不符、已过时或与用户当前明确要求冲突的记录，应核实适用范围；重大冲突应向用户说明，不用旧记忆否定新指令。

### 2.2 Remember：写入时机与价值判断

核心问题是：**未来的 Agent 若不知道这件事，是否会重复劳动、重复犯错、违背约定或作出较差判断？**

三种写入触发：

1. **用户意图触发**：用户明确说“记住”“保存下来”“以后都按这个来”“下次碰到要……”等，应整理并保存。仅说“总结一下”通常表示请求当场总结，**不能一律视为要求持久保存**；须结合上下文判断。
2. **价值触发**：工作中产生重要决定、有效方案、失败教训、关键限制或可复用知识时，可以主动记录，不必等到任务结束。
3. **阶段触发**：阶段结束、任务完成或上下文压缩前，回顾是否有尚未记录的重要信息。

**推测可以记**：重要但未验证的发现可写成“已知事实 / 当前推测 / 待验证项”，绝不能把假设当作结论；验证后应优先修正原记录，保留必要依据或证伪过程。

**Action Rule 单独对待**：

- 用户明确要求长期执行的规则：可按要求保存。
- Agent 自己从一次或多次经历中概括出的“以后必须如何做”：**先征求用户确认**，再写为长期行为规则。
- 本次任务的临时步骤：不能自动提升为长期规则。

### 2.3 Abstraction：记忆以知识点为单位，而不是只能按事件归档

希望并存的三个抽象层次：

| 层次 | 表达什么 | 示例（示意） |
| --- | --- | --- |
| **Event / Episodic** | 一次具体事件的背景、经过、结果 | 某次 Oracle 死锁排查及最终处理办法 |
| **Knowledge** | 可从经验中复用的事实、方法或机制 | 不同资源加锁顺序可能引发循环等待 |
| **Principle** | 有边界、有依据的抽象判断原则 | 对共享资源尽量保持一致的获取顺序 |

这**不是强制三级流水线**。一个知识点可以直接保存；不是每次完成事件都要生成三条。保持独立的事件细节，同时将重复结论提炼和更新为可复用知识。

允许在 Content 中引用真实的其他记忆 ID，注明“依据 / 补充 / 反例 / 演化”等关系。**当前只是正文引用**，不能假定系统会自动建立双向关系、引用完整性约束或图检索能力；暂不增加 Schema。

### 2.4 Deduplication：保存前先找已有记录

新信息准备落库时，默认检索相关记忆，决定：

- **新增**：新事件、知识或原则有独立价值。
- **更新**：已有知识可以补充、纠错、澄清适用范围，或已有原则得到新依据 / 反例。
- **跳过**：现有记忆完全覆盖且没有新增价值；用户明确要求“记住”时应告诉用户已被已有记录覆盖，不能假装写入成功。

**文字相似不代表重复**：不同事件可以各自保留，重复知识应合并。更新不应不加区分地抹去必要的历史依据。删除旧记忆仍须按权限规则处理。

### 2.5 Organization：沿用现有元数据，不急于修改 Schema

| 字段 | 职责 | 示例 |
| --- | --- | --- |
| **Namespace** | 项目或工作范围 | `atos-next` |
| **Categories** | 记忆性质 | `event`、`knowledge`、`principle`、`decision`、`action-rule`、`preference` |
| **Keywords** | 主题与概念 | `concurrency`、`git`、`deadlock` |
| **Anchors** | 明确对象或标识 | `ORA-00060`、`AGENTS.md`、类名或配置键 |
| **Content** | 事实、推测、结论、适用条件和引用 | 具体记忆正文 |

核心 Categories 尽量统一，**不做强制封闭枚举**；确有需要时允许扩展。按当前工具约定，一条记忆最多 3 个 Categories、5 个 Anchors；字段准确含义与参数以 MCP 工具说明为准。`action-rule` 用于标识长期行为规则，供关键操作前检索。

新分组需要按工具提示确认；保存和查询明确指定当前项目 Namespace，不未经授权跨项目混写。Namespace 是分组，不是访问权限隔离。

### 2.6 Report：以使用效果反馈检索质量

- Agent **主动反馈**，不需要等用户明确要求。
- 评价的是记忆在**当前任务**中的真实贡献，而不是相关度分数。
- 实际使用后发现有帮助，给予正向评分；认真阅读后发现无帮助或误导，也应如实评价。
- 仅看见搜索标题、没有充分阅读或暂无法评价，不必凑评分。
- 遵守 MCP `report` 的调用限制：例如有效搜索上下文、对应 `search_id`、评分范围、仅对有效非空结果中的记忆评分，以及工具规定的时效和次数限制。

### 2.7 Safety：用户决定是否改变长期行为

- 当前事实、当前用户明确指令优先于历史记忆；重要冲突要说明。
- 不保存密码、密钥或无关隐私。
- 删除、清空或破坏性覆盖记忆须取得明确授权。
- 对于用户要求保存的内容，只有真正完成 MCP 写入后才能声称“已保存”；工具失败要如实说明。

## 3. 正式长期指令 V2（已确认，可直接放入项目指令文件）

> **本节是规范原文（single source of truth）**。后续调整 V3 时，优先修改本节并同步更新决策记录。

```markdown
## Remember Me — 长期记忆规则

使用 Remember Me 管理项目长期记忆。Namespace：`<项目 Namespace>`。未指定 Namespace 时先询问，不擅自设置跨项目默认值。

1. **主动回忆**：在理解问题、分析方案和执行任务时，自然联想相关记忆；信息不足时，尝试不同线索继续检索，必要时读取全文。找到足够依据或继续检索已无明显价值时停止，不编造历史信息。

2. **复用经验**：需要探索环境、寻找操作方法或反复尝试前，先回忆是否存在已有做法，核实后优先复用。下一步方法明确可靠时无需机械检索。

3. **决策与行动**：重要决策前回忆历史经验、既有约束和失败教训；执行提交、部署、删除等关键操作前，检查相关的长期行为规则（如 `action-rule`），即使操作方法已经明确。

4. **主动积累**：用户明确要求记住或长期沿用的信息应及时保存。工作中发现重要决策、经验、解决方案或可复用知识时主动保存；阶段结束或上下文压缩前检查是否遗漏。单纯要求总结不等于要求持久保存。

5. **提炼知识**：以独立知识点组织记忆，保存有价值的事件、知识和抽象原则，必要时引用相关记忆 ID。区分事实、推测和待验证结论，注明依据与适用范围，避免过度泛化。自行归纳的长期行为规则须经用户确认后保存。

6. **去重与演进**：写入前检索已有记忆，判断新增、更新或跳过。保留有独立价值的事件，合并重复知识，持续完善已有原则；修正过时或错误结论时保留必要的原因与证据。

7. **组织与反馈**：保存、检索时使用本项目 Namespace，不擅自跨项目混写。合理填写 Categories、Keywords 和 Anchors，优先复用合适的现有分类。实际使用或评估检索结果后，通过 `report` 如实评价有用程度；无法判断时不强求评分。

8. **事实与安全**：以当前事实和用户明确指令为准，核实记忆的适用性，遇到重要冲突时说明。不保存密码、密钥或无关隐私；删除、清空或覆盖记忆前取得明确授权。工具失败时如实说明，不声称未完成的操作已经成功。
```

**使用时**：把 `<项目 Namespace>` 替换成对应项目的实际分组名；不要把尖括号占位符原样当作 Namespace 使用。

## 4. 一键安装提示词（安装指令与长期规则分离）

安装请求只是**一次性指示 Agent 保存规则**，不应该重复写入项目长期指令文件。当前产品使用的安装要求如下（保留既有操作意图）：

```text
请把下面的记忆规则保存为当前工作项目的长期指令。找到当前 AI 工具会加载的指令文件，没有就创建；保留原文，合并重复规则。分组名未填写时先问我，不要设为所有项目的默认值。完成后告诉我文件完整路径和生效步骤；无法保存时，说明原因并给出手动操作方法。

以下是要保存的记忆规则：
```

**完整的一键复制内容 = 上述安装请求 + 第 3 节完整的八条规则**。Help 的“复制保存请求（含记忆规则）”应在运行时组合这两部分，避免在本设计文档中维护两份不同版本的 V2 正文。

安装流程应满足：

1. 找到**当前 Agent 实际会加载**的项目指令文件（例如 Codex/OpenCode 的 `AGENTS.md` 或 Claude Code 的 `CLAUDE.md`），不能臆测路径或写入不会生效的位置。
2. 询问并确认具体 Namespace；只作用于当前项目，保留文件原有其他指令。
3. 如果存在 V1 / 重复条目，合并或替换对应 Remember Me 规则，避免两套冲突规则并存；如果已有内容存在实质冲突，先告知用户。
4. 保存后报告完整文件路径、修改范围以及让规则生效的方法（如按客户端要求重启会话）。
5. 无权限修改文件、无法确认加载机制或实际写入失败时，如实说明，不声称完成。

> 注：第 3 节的八条 V2 长期规则已经在讨论中确认；本节的安装文案沿用已有实现，尚未针对所有客户端逐一实测。

## 5. 为何由 V1 演进到 V2

| 维度 | V1 | V2 |
| --- | --- | --- |
| Recall | “开始任务前检索” | 在思考全过程按需回忆，可多轮检索 |
| 操作方法 | 未单列 | 再次摸索前先查可复用的方法 |
| 决策、事件 | 无专门检查 | 决策前找历史约束，关键行动前找 `action-rule` |
| 写入触发 | 决策、解决问题、阶段结束 | 用户明确意图 + 长期价值 + 阶段检查 |
| 内容层次 | 主要是事件及结论 | 事件、知识、原则；可引用且避免过度泛化 |
| 不确定性 | 未单列 | 可以记录推测，但必须标记并在验证后修正 |
| 质量维护 | 优先更新避免重复 | 新增 / 更新 / 跳过；区分独立事件与重复知识 |
| Report | 有用时反馈 | 只基于实际贡献正负评价，不凑评分 |

## 6. 后续迭代的评审方式

以后希望调整规则时，按下列顺序讨论，先记录问题再改提示词：

1. **现象**：Agent 在什么任务、什么阶段表现不理想？提供可复现的对话或工具调用例子。
2. **归属**：问题属于 Recall、Remember、Abstraction、Deduplication、Organization、Report 还是 Safety？
3. **目标行为**：希望 Agent 在触发条件下实际做什么？什么情况下可以不做？
4. **代价 / 风险**：是否引入无意义的 MCP 调用、更多低价值记忆、错误推断、过度管控或权限风险？
5. **修改范围**：优先调整一条简洁规则；仅在无法表达时增加条目。复杂技术细节应写入 `/read-me` 或 MCP 工具说明。
6. **验证**：用相关任务的实际 Agent 行为评估，而不只看提示词措辞是否漂亮。

### 6.1 建议回归场景

| 场景 | 期望验证 |
| --- | --- |
| 查询本地数据库 | 需要重新寻找连接方法时，先检索已有操作经验 |
| 已有可靠的下一步 | 不为完成形式而机械查询记忆 |
| 重要设计选择 | 检索历史决策、约束和教训；发现冲突及时说明 |
| 准备 Git Commit | 查找并应用当前项目有关提交的 `action-rule`（若存在） |
| 用户说“记住这个决定” | 实际保存并报告结果；有重复时妥善合并 |
| 用户只说“总结一下” | 进行总结，不默认将其当作持久保存命令 |
| 排查发现一个尚未验证的原因 | 可以保存推测，但标明证据与待验证项 |
| 连续出现相似故障 | 保留独立事件，更新共享知识或原则 |
| 读到无关或误导记忆 | 有充分依据时使用有效 `search_id` 给出如实反馈 |
| 记忆与当前明确要求冲突 | 当前要求优先，重大差异说明 |

### 6.2 待以后明确的细节（当前不阻碍 V2 使用）

- **“更新”与“覆盖”的边界**：V2 鼓励对已有知识做准确的增量更新，同时要求“覆盖记忆前授权”；后续可把破坏性替换与常规纠错更新区分得更精确，以避免 Agent 过度请求确认或误覆盖重要历史。
- **关系索引**：正文关联 ID 只是软引用，是否需要真正的双向关系及完整性约束，另作独立产品设计。
- **`action-rule` 的稳定性与作用范围**：长久生效的规则、一次性任务约束和跨项目规则是否需要更多边界说明，视实际使用反馈再决定。
- **Agent 触发的可靠性**：长期指令属于软约束；对必须严格执行的关键操作，应考虑客户端原生 Hook、自动检查或其他确定性机制。

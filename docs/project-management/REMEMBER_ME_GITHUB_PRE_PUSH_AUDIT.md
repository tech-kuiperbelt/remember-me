# Remember Me — GitHub 首次 Push 前只读检查任务

## 任务背景

Remember Me 是面向 AI Agent 的持久记忆 MCP 服务，包含 Web 管理界面。当前准备首次将已有本地 Git 仓库推送到 GitHub，**暂不公开发布**。

已知情况（请重新核实，以当前本地状态为准）：

- 本地项目目录：`~/me/remember-me`
- 本地分支：`master`
- 本地已有 Git 提交历史；最近看到的提交为 `ee2894d`
- 远程仓库：`origin = git@github.com:tech-kuiperbelt/remember-me.git`
- GitHub 仓库目前是空的 **Private** 仓库
- GitHub SSH 验证已成功
- 工作区此前存在 **7 个未提交的修改**（可能已变化），请勿覆盖或提交
- 未来可能将此仓库改为 **Public** 并发布首个 Release，但本次目标只是安全完成第一次 Push

## 核心目标

回答两个问题：

1. **现在能否安全地将已有提交历史 Push 到 Private 仓库？** 如不能，列出必须先处理的阻塞项。
2. **未来将仓库设为 Public 之前，还必须处理什么？** 明确区分此类问题与第一次 Private Push 的阻塞项。

遵循最小必要原则：不为发布重构、不引入不必要的 CI/CD、PyPI、Docker Hub 或新的工具链。

## 硬性约束

**本任务为严格只读审计。**

- 不修改、新建、删除任何项目文件；不要自动修复。
- 不执行 `git add`、`commit`、`push`、`pull`、`fetch`、`reset`、`clean`、`rebase`、`checkout`、`switch` 或其他可能改变 Git 状态/工作树的操作。
- 不创建或修改 GitHub 仓库、Release、分支、标签、权限。
- 不运行会写入项目数据的构建、测试、应用启动、数据库迁移或模型下载。
- 如果某项验证必须修改状态，只描述验证方法，**不要执行**。
- 可执行只读的 Git、文件元数据和静态内容检查；尽量避免打印敏感内容或大量文件全文。
- 发现疑似密钥、密码、Token、私有数据时，**只报告文件路径、版本/提交标识、风险类别和建议**；不要在输出中复制或展示秘密值。必要时对路径中的个人信息做脱敏。
- 不将代码、配置、历史内容发送到外部服务，不调用外部在线扫描。
- 对无法完全确认的事项明确写明“未验证”，不要推测成“安全”。

## 检查范围

### A. Git 状态与首次 Push 范围

- 当前目录是否为正确的项目根目录；`git status -sb`、当前分支、HEAD、`origin` 配置是否符合预期。
- 工作区是否有未提交、未跟踪文件；明确说明 **Push 仅包含已提交内容，不包含工作区修改**。
- 是否存在本地额外分支、标签及其他引用；说明执行 `git push -u origin master` 将推送哪些提交，注意不要把“其他分支存在”误判为一定会被此次 Push 上传。
- 识别嵌套 Git 仓库、submodule、Git LFS 或可能影响首次推送的特殊配置（如有）。

### B. 敏感信息与私人数据（重点）

- 检查**当前已跟踪文件**，也检查**将随 `master` 推送的历史提交**（不能只看 HEAD），寻找曾经提交的 API Key、Token、密码、SSH 私钥、证书私钥、`.env`、个人数据库、真实业务/用户数据、内网地址与其他不应公开的信息。
- 重点检查配置文件、测试样例、脚本、文档、历史版本，以及 SQLite/NDJSON/JSON 导出文件。
- 区分真实秘密与示例占位符，避免误报；如果难以确认，标记为“需人工确认”。
- **如果敏感信息曾进入将要 Push 的 Git 历史，即使最新版本已删除，也必须报告**；`.gitignore` 不能消除历史泄露。
- 不要自动尝试历史改写或密钥轮换；给出最小修复方向供用户决定。

### C. `.gitignore` 与不应入库的文件

- 检查现有规则是否覆盖实际使用的运行路径，而不只是泛泛地列出扩展名：
  - SQLite 数据库及 WAL/SHM；NDJSON 备份或镜像；用户记忆数据、日志与临时文件
  - 下载或生成的 BGE-M3 / ONNX / 量化模型及缓存、embedding 索引
  - 虚拟环境、Python 缓存、Node 依赖、浏览器测试产物、前端构建产物及其他本地生成文件
  - `.env`、本地覆盖配置、凭据、IDE/OS 临时文件
- 同时检查：已经被 Git 跟踪的文件**不会因为后来添加 `.gitignore` 而自动取消跟踪**。
- 对每一个可能有问题的规则给出真实路径/匹配依据，避免建议盲目忽略需要版本管理的配置模板或锁文件。

### D. Git 大文件与二进制

- 检查当前跟踪文件及将推送的历史对象中是否存在明显的大文件或不必要的二进制、数据库、模型文件。
- 重点标记大于 **50 MiB** 的文件/对象，并明确指出大于 **100 MiB** 的 GitHub 普通 Git 文件上传阻塞风险。
- 说明问题位于当前树还是历史提交，以及是否会随着首次 `master` Push 一起上传。
- 模型默认采用独立下载策略，不建议直接把模型文件纳入 Git 历史；本次不要求实现下载器。

### E. 基础发布材料与可运行性（只做静态检查）

- README：是否能说明产品定位、基本功能、最简安装/启动方式、配置与 Codex `/mcp`、OpenCode `/sse` 接入方式。
- LICENSE：是否已有许可证；缺失时标记为**公开开源前需要决策**，不默认判定为 Private Push 阻塞项，也不要擅自选择许可证。
- 配置模板：是否存在安全的示例配置，是否包含环境专有路径/个人信息。
- Dockerfile / Compose、依赖锁定、构建说明、模型首次下载行为：静态判断能否让第三方复现；不能静态确认的标为“未运行验证”。
- 不要求现在就实现打包、Release、自动化构建或多平台支持。

## 输出格式

请**直接在对话中输出**一份简洁的 Markdown 审计报告，**不要在项目中写报告文件**：

### 1. 结论

- `Private 首次 Push：可以 / 有条件可以 / 暂不可`，附一句理由。
- `未来公开仓库：可以 / 尚有阻塞项 / 未充分验证`，附一句理由。
- 审计范围和未覆盖项（尤其是否真正覆盖将推送的历史提交）。

### 2. 阻塞项

使用表格：`优先级 | 问题 | 证据（路径/提交，不包含秘密值） | 风险 | 最小处理建议`。

请分成：
- **P0：首次 Private Push 前必须解决**（例如敏感数据不应进入远端，即使 Private）。
- **P1：变成 Public 前必须解决**（如果 Private Push 暂时可行）。

### 3. 非阻塞改进

列出最多 5 项真正有价值的优化；不要提出无关重构。

### 4. 当前状态摘要

包括：分支、HEAD、remote、未提交文件数量、当前跟踪文件数量、有无大对象、README/LICENSE/.gitignore 状态（能确认多少写多少）。

### 5. 推荐的最少操作步骤

按照**先处理阻塞项 → 人工复核 → 首次 Push**的顺序列步骤；不要执行。

只有在确认没有阻塞项后，才把下面的命令列为“待用户手动执行”，**不要替用户运行**：

```bash
git push -u origin master
```

## 判定原则

- 不能因为仓库当前是 Private 就忽略真实密钥或个人数据泄露风险。
- 不要把 README 美化、CI/CD、正式 Release、许可证选择等一概设为首次 **Private Push** 的阻塞项。
- 对安全检查不得只扫描当前工作区；重点是**随 `master` 首次上传的完整可达提交历史**。
- 保留现有 `master` 分支和提交历史，除非审计发现不得不处理的真实风险；本任务只提出方案，不执行修改。

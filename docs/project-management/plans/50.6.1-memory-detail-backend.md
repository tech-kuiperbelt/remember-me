## 1. 目标与现状

为 Detail 编辑补齐“明确清空摘要”的能力，验证现有更新接口支持分类、关键词和 anchors 编辑。采用现有 Admin HTTP → MemoryService → Storage 调用链，无新 endpoint、数据库字段或迁移。

现状核对：

- GET `/api/memories/{id}` 返回完整记忆；不存在返回 404。
- PUT 同路径返回 `{ "success": true }`，可能附带既有 `categories_dropped`／`categories`，不返回完整记忆。前端成功后必须 GET 重读。
- DELETE 同路径返回成功状态；不存在返回 404。
- `normalize_summary` 将空白和 null 都转为 None，当前不能显式清空。正文实质变化且未提供可用摘要时，存储层重新提取摘要；metadata-only 或空白等价的正文更新保留摘要。
- metadata 采用浅合并；仅显式提供的维度替换，空数组清空。正文实质变化且未显式提供 anchors 时清除旧 anchors。
- Service 仅在提供 text 时执行正文 embedding；分类／关键词向量由已有路径处理。

## 2. 前后端公共契约

### 2.1 Admin PUT 的 Summary 语义

| `summary` 输入 | 行为 |
|---|---|
| 未传或 null | 沿用既有更新策略：未改正文则保留；正文实质变化则重新提取 |
| 非空字符串 | trim 后保存，不使用自动摘要覆盖 |
| 空字符串或纯空白字符串 | 明确清空，数据库保存 null；即使同时改变正文也不生成摘要 |
| 其他类型 | HTTP 400，`response_code=invalid_request`；在业务调用前拒绝 |

**null 不表示清空，也不无条件表示“不变”**：它与省略一样沿用旧策略，正文实质变化时仍会派生摘要。只有 Admin PUT 的显式空白字符串表示清空。MCP 的 update、低层 API 默认调用、Add、导入、恢复保持原有行为。

本次 Admin PUT 有两项明确的兼容变化：空白摘要从“沿用回退策略”改为“清空”；非字符串且非 null 的摘要（如 123、false、数组、对象）从静默当作缺省值改为 HTTP 400。实施报告和接口说明须同时记录。

前端要求：正文变化时一并提交表单里的当前摘要，包括空字符串；仅改其他字段且摘要未变时可以省略。**相较旧弹窗仅发送 text／namespace，新抽屉编辑正文不再为无摘要记忆自动派生存储摘要**：GET 返回 summary=null，表单为空，修改正文后提交 summary=""，存储仍为 null。有摘要时同样保留表单当前值，除非用户编辑或清空；这是已确定的“表单值为准”行为变化。

GET 详情返回存储摘要，不做派生；列表前端 deriveSummary 和 LLM 侧 _prepare_for_llm 的展示回退保持原有行为。验收必须分别断言存储仍为 null、详情显示无摘要，以及列表／LLM 仍能从新正文得到展示摘要，不得将展示回退写回数据库。

### 2.2 其他字段

| 字段 | 约定 |
|---|---|
| text | 原始正文，省略表示不改；沿用 embedding 输入验证与错误响应 |
| namespace | 既有规范化、长度、保留词和未知空间确认流程；省略表示不改 |
| metadata.categories | trim／lowercase／去重；最多 3 个，保留既有超额处理及返回提示 |
| metadata.keywords | trim／lowercase／去重；不增加筛选器的 20 项写入限制 |
| metadata.anchors | 最多 5 个；NFKC、空白折叠、大小写保留、ASCII 不区分大小写去重，单项最多 128 个 Unicode 字符，严格拒绝非法输入 |
| 其他 metadata | 请求未提供的字段保留；前端不得回传整份旧 metadata 覆盖无关字段 |

三个维度的空数组表示清空。允许新分类／关键词值，复用现有生成索引值向量与事务路径。anchors 不生成向量。

GET 返回已存储的 metadata.anchors 原值供前端回显／回传，保留值、大小写和顺序；不存在该键时不生成锚点，也不在读取时规范化历史值。写入仍经严格校验。

正文变化时，前端显式提交用户检查后的当前 anchors，包括空数组；后端不会替遗漏 anchors 的调用方补回旧值。任何非抽屉 Admin 写入方若实质改变正文而不带 metadata.anchors，仍会清除旧 anchors。端到端验证须覆盖 GET → 仅改正文并回传已有 anchors → GET 原值保留，以及同样改正文但省略 anchors → GET 旧锚点清除。

### 2.3 请求示例与错误

仅清空摘要：

```json
{"summary":""}
```

修改正文、保留用户填写的摘要并明确替换锚点：

```json
{"text":"新正文","summary":"当前摘要","metadata":{"anchors":["MemoryService"]}}
```

清空分类、更新关键词，不影响其他 metadata：

```json
{"metadata":{"categories":[],"keywords":["sqlite","locking"]}}
```

PUT 成功仍返回 `{"success":true}`；前端不得当作记忆对象。已有 404、namespace 确认、invalid_anchors、embedding 输入限制及维护门禁响应沿用。不得用统一的新错误结构覆盖既有端点差异。

## 3. 实施方案

### 3.1 Admin 与 Service

- Admin 先验证 summary 为字符串或 null；检测显式空白字符串，转换为内部 `clear_summary=True`，summary 向业务层传 None。
- 给 `MemoryService.memory_update` 增加 keyword-only `clear_summary: bool = False`，不改变已有位置参数顺序。
- 内部 clear_summary 非布尔时抛 TypeError；为 true 且规范化后的 summary 非空时抛 ValueError。两者属于内部调用契约错误，校验先于 embedding 和写入；直接调用者收到原异常，若因代码错误穿过 Admin 边界，沿用 HTTP 500，不映射为用户输入 400。
- 正常 Admin 转换只产生布尔开关，且清空时恒传 summary=None，上述内部异常不可由合法 HTTP 输入触发。公开 summary 类型错误由 Admin 自己抛 InvalidRequest 并映射为 400；Service 不导入 transport.InvalidRequest，也不新增全局 ValueError→400 映射。
- clear_summary 是内部能力，不新增 MCP schema 字段，也不将其列为公开 HTTP 请求参数。旧调用默认 false。

### 3.2 Storage 与摘要策略

- 给 MemoryStorage.update、SQLiteStorage.update、DualStorage.update 增加兼容的 keyword-only clear_summary 参数；核对 tests/test_storage_contract.py 等既有调用点，保持不传新参数的调用兼容。当前 tests/ 没有实现 update 的存储替身，不预设需要修改不存在的替身。
- `summary_for_update` 增加该开关，true 优先返回 None；false 完全保留现有策略。
- SQLite 在现有锁和更新事务内处理摘要，继续执行现有 updated_at、version、索引及 outbox 更新。不要在 Admin 额外做第二次 SQL 清空。
- DualStorage 原样透传；JSONL 同步与导出依现有机制携带 null，不增加特殊格式。
- 不因摘要清空提交 text 或重新生成正文 embedding。仅摘要清空也算一次正常更新，更新时间随之变化。由此该记忆在默认 updated_at 降序 Browse 中可能前移至顶部（并非置顶字段或保证固定首位），也可能改变时间筛选匹配；沿用正常更新的排序／筛选语义，不为清空摘要设置例外。前端保留当前页和滚动位置，不强制跳到第一页寻找该记录；null 与空白等价的 clean 表单不会单独触发无效清空。

### 3.3 边界

不扩展并发冲突检测、自动摘要生成、关键词配额、anchors 业务规则或通用 PATCH 协议。GET／PUT 分两次调用，重读可能看到其间的其他更新；沿用当前并发行为。

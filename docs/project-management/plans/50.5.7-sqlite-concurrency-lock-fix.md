## 1. 问题与证据边界

SQLiteStorage 共用一个 `check_same_thread=False` 的连接，但锁保护不完整：`get()` 直接访问连接；`_row_to_dict()` 会补查 active profile 的向量，而列表、outbox 读取和全文搜索存在释放锁后调用它的路径。时间筛选通过 SQLite UDF 回调 Python，未受保护的并发连接访问存在 SQLite 内部互斥锁与 Python GIL 交叉等待的风险。

已在临时数据库复现：启用 embedding profile，200 条固定三维向量记录，4 个线程各执行 300 次带时间筛选的列表查询，8 秒后仍未完成。线程栈分别停在 `_row_to_dict()` 的查询、列表查询以及应用锁等待。仅在复现脚本中给结果转换补上同一把锁后，1,200 次调用约 0.36 秒完成。沙箱外亦复现卡死，加锁对照组耗时 0.357 秒。脚本 `/tmp/remember_lock_profile_probe.py` 和栈 `/tmp/remember_lock_profile_stack.txt` 是临时调查产物，实施时须转化为仓库内可重跑的测试，不能依赖这些文件长期存在。

这证明当前代码存在并发卡死缺陷，与此前线上并发查询后无响应高度吻合；线上当时未取得线程栈，不能认定已最终证明同因。重启后暂未复现不构成修复证据。

取消测试作为独立线索处理：旧 PID 740961 检查时为 `Sl`，打开的是 `/tmp` 下测试数据库，不是生产数据库，也不是严格意义的僵尸进程。取消测试沙箱内挂起时，业务线程已空闲，事件循环在 `select` 等待；沙箱外相同取消测试 10 项全部通过，耗时 0.56 秒。没有证据将该现象归因于同一个 SQLite 缺陷，也没有旧进程自身的线程栈证明其原因。调查没有终止该旧进程。

## 2. 目标与实现

修复共享连接的锁保护缺口，保留微秒精度、时区归一化、严格时间边界和现有查询语义。使用现有 `threading.RLock`，不增加新锁、不更换连接架构。

在 `app/storage/sqlite.py` 中落实以下规则：

- `get()` 从查询、取行到结果转换全程持锁，兼容 `update()` 等已持锁调用方的重入。
- `_row_to_dict()` 内补查向量的连接操作自行持锁，覆盖 `execute()` 与 `fetchone()`，避免辅助函数绕过保护。
- `list_memories()`、`get_unsynced_records()`、`_search_fts()` 将依赖数据库的结果转换纳入原查询锁范围，避免读取记录与补查向量之间插入其他操作。
- 检查全部连接访问及游标消费路径：在线共享连接必须持锁；初始化或离线独占路径明确前提。补充锁使用约定，防止后续遗漏。
- 纯内存计算继续放在锁外，包括语义相似度计算；不把 embedding 推理、文件同步、线程等待移入 SQLite 锁。

公开 API、返回结构、数据库 schema、事务提交行为保持不变。不调整取消请求的 reader 槽位生命周期，不修改生产数据。旧 pytest 清理单独处理，不作为修复前置条件。

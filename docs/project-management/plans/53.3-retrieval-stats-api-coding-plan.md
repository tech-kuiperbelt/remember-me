# 53.3 Retrieval Statistics API Coding Plan

日期：2026-10-10  
状态：后端 API 已实施并通过测试（commit `7d36d2c`）；Retrieval 前端另行实施。  
设计依据：[RETRIEVAL_STATS_API_DESIGN.md](../../design/RETRIEVAL_STATS_API_DESIGN.md)（已同步本计划口径）。

## 1. 目标与范围

新增只读 `GET /api/stats/retrieval`，统计保留 Audit 中的 MCP 检索行为与显式反馈，采用基本一致性。

实施范围为 API、测试及文档修订；Retrieval 前端另行实施。保持现有 Memory Stats、Audit 查询、MCP 工具和审计写入格式不变，不增加数据库表、缓存、迁移或依赖。

实施前同步修订 `RETRIEVAL_STATS_API_DESIGN.md`，删除固定历史日期及严格快照要求，并同步本计划中的已确认口径。

## 2. API 与统计口径

### 请求和时间窗口

- `days` 默认 7，仅接受 7／30／90；`timezone` 必填，使用标准库 `zoneinfo` 校验。
- `namespace` 省略表示 All；显式空白拒绝。trim 后保留大小写，复用当前活跃空间加默认空间的存在性校验。
- 拒绝未知参数和重复参数，沿用 Admin 的 HTTP 400 错误格式。
- 每次请求只取一次评估时刻。窗口从本地起始日零点到评估时刻，包含今天，不使用固定小时数代替日历日。
- 7／30 天返回完整日桶，包括零值日期；90 天按周一开始的自然周返回，首尾桶裁切到请求范围。
- 周桶字段固定为 `start_date`、`end_date`、`start_utc`、`end_utc`、`count`；日期表示实际覆盖日期。相邻桶采用左闭右开边界，最后一个桶包含评估时刻。
- 未知时区返回 400；服务器缺少时区数据库时返回 503 和明确错误码，不静默改用 UTC。

### 搜索计数

- 仅纳入 `context.source="mcp"` 的四类搜索：semantic、lexical、anchor、meta。来源无法识别的记录跳过并计入诊断。
- 不设置历史日期或 Schema 版本门槛；按各指标需要的字段判断记录可用性。
- 有合法带时区时间戳、工具名和 `ok/error` 状态即可参与调用计数，不要求 `search_id`。
- `status=ok` 对应“正常返回次数”；结构化空结果仍计入，`status=error` 对应失败次数。
- 正常返回且 `result.items` 为非空数组，才计入 `non_empty_searches`。结果字段缺失不推断为空，记录数据质量提示。
- 搜索按请求中的 Namespace 归属；未指定空间的调用只进入 All。已清空空间的历史保留在 All，但不增加历史空间筛选入口。

### 显式反馈

- 使用成功 MCP `report` 的 `params.ratings`、关联 ID 和 `result.feedback_context.analysis_group`。
- 仅排除明确的 `declared_test`；纳入人工评价、LLM 任务、未分类及未声明反馈。关联测试搜索仍计入调用量。
- 每项评分必须是 `-10..10` 整数，排除布尔值；Memory ID 必须属于关联正常搜索的返回集合。
- 时间和 Namespace 筛选作用于搜索事件；反馈按关联搜索归属，扫描保留日志中的后续反馈，但不纳入晚于评估时刻的记录。
- 按 `(search_id, memory_id)` 去重：最后有效非测试评分生效；同时间戳按旧文件到新文件、文件内行号决定顺序。
- 缺少关联 ID 的非空搜索仍进入反馈覆盖率分母；不补造反馈关系。
- 覆盖率分母为非空正常搜索数，零分母返回 `null`；有分母但无反馈返回 0。无评分时平均分为 `null`，中性 0 是有效评分。

保留设计中的 `scope/search/feedback/data_quality` 响应结构；覆盖率和平均分保留两位小数，分布返回整数计数。

## 3. 读取与聚合实现

在 `app/operations/retrieval_stats.py` 增加独立只读聚合模块，由 Admin 路由通过现有工作线程调用。Namespace 校验复用 Service 能力，不把文件扫描放到事件循环或控制线程池。

- 从运行时 AuditJournal 取得路径与保留数量，不写死文件名或 `.9` 上限，不复用有条数限制的 `read_events()`。
- 两遍流式扫描：第一遍计算搜索指标、保留全局关联 ID，并保存选定范围内搜索的必要结果 ID；第二遍处理反馈。只保存关联和聚合所需字段，不保留查询、摘要或完整事件。
- 每个文件按打开时长度有界读取；追加内容允许下次请求纳入。通过文件身份和大小变化识别轮转／截断，避免同一文件重复计数。
- 检测轮转变化后丢弃该次中间结果，最多重试整个聚合一次；第二次仍变化则返回该次可读结果和 warning。整个重试过程沿用同一评估时刻。
- 不获取 Audit 写锁，不提供快照承诺。无法保证日志时间单调，因此不因遇到一条窗口前记录就提前停止。
- 初始没有日志文件时返回零统计及 `no_audit_history` 提示；正常缺少轮转文件不报错。权限或实际 I/O 错误返回非 200，错误响应不暴露路径。
- 损坏 JSON／编码行跳过并计数；并发追加留下的不完整尾行跳过并给出提示。
- 重复且冲突的搜索 ID 不用于反馈关联，报告诊断；调用量仍按搜索事件计数。

`data_quality` 明确属于全局扫描诊断，包括损坏行、缺必要字段、排除的测试报告、无法匹配的报告和读取变化；两遍扫描不能重复累计同一诊断。`unmatched_reports` 按报告事件计数，不把“搜索存在但不在选定范围内”算成无法匹配。

`available_from` 改为最早保留的、可参与搜索调用统计的时间戳，无数据为 `null`。`coverage_complete` 在 v1 返回 `null`，具体读取问题通过 warning 表达，不凭第一条记录时间猜测历史完整性。

## 4. 测试与性能验证

新增独立聚合与 Admin API 测试，使用合成日志和可注入时钟：

- 参数缺失、重复、非法值；有效／无效／已清空 Namespace；缺少时区数据库。
- 7／30 日桶、90 天周桶、跨年、夏令时、零点及当前未结束日期。
- 四种模式零值补齐；失败搜索无 ID；正常空结果；缺失结果字段；旧记录按字段能力纳入。
- MCP 与 Admin 来源区分；跨空间搜索只进入 All；报告 Namespace 为 null 时仍正确关联。
- 人工／LLM／未声明反馈纳入，测试反馈先排除；重复评分、中性评分、非法评分、结果成员不匹配、迟到反馈。
- 全局诊断与业务范围分离；丢失搜索、重复搜索 ID、损坏行、不完整尾行、无文件、读取错误。
- 并发追加、轮转和截断；最多一次重试；不持有写锁；未阻塞事件循环。
- 不变量：正常＋失败＝总量，模式与趋势分别求和等于总量，已评分搜索数不超过非空正常搜索数。

使用约 100MB 合成保留日志测量请求耗时和峰值内存，记录环境及结果；本轮不据此自动引入缓存。运行新增测试、现有 Audit／Report／Stats API 定向回归及完整 pytest。

## 5. 完成标准

API 返回可核对的统计结果；零值、未知覆盖情况与读取错误能明确区分；所有已确认口径进入设计文档和实施记录。完成测试和性能记录后交付 review，本轮不接前端、不提交或重启生产服务。

## 6. 实施记录（2026-10-10）

**已实施**

- `app/operations/retrieval_stats.py`（新增）：独立只读聚合模块。`collect_retrieval_stats(path, max_files, days, tz, namespace, now)`；`resolve_timezone` 区分未知时区（`UnknownTimezone`→400）与缺失时区库（`TimezoneDatabaseUnavailable`→503）；`journal_paths` 同时支持运行时 `AuditJournal` 与 legacy `app.audit` 模块；两遍流式扫描；有界读取 + 文件身份/大小快照 + 最多一次重试；`data_quality` 为 `skipped_malformed_lines`/`skipped_unrecognized_source`/`excluded_test_reports`/`unmatched_reports`/`conflicting_search_ids`/`warnings`。
- `app/transport/admin.py`：新增 `GET /api/stats/retrieval`（`read` 策略，经 `_run` 业务线程），参数/时区/Namespace 校验与错误码；Namespace 复用 `normalize_namespace`/`validate_namespace_name`/`known_namespaces`。
- `docs/design/RETRIEVAL_STATS_API_DESIGN.md`：按 Step 0 同步能力判断、`source=mcp`、503 时区库、去重平局、`available_from` 语义，并补充 `data_quality` 字段。
- `tests/test_retrieval_stats.py`（新增 26 例）+ `tests/test_admin_routes.py` 路由顺序断言。

**口径定稿（与计划一致）**

- 搜索：仅 `context.source="mcp"` 的四类；有合法带时区 `ts`+工具名+`ok/error` 即计数；`available_from` 取全部保留 eligible 搜索的最早 `ts`（与请求窗口无关）。
- 反馈：成功 report；先排除 `declared_test` 再按 `(search_id, memory_id)` 去重（旧文件→新文件、文件内行号为序，后者胜）；`m_id` 必须属于关联正常非空搜索返回集合；`ts` 晚于评估时刻排除；分母=范围内非空正常搜索，零分母返回 `null`，有分母无反馈返回 `0`；无评分为 `null`（0 是有效评分）。
- 未知时区 400 `invalid_timezone`；缺时区库 503 `timezone_database_unavailable`；读取失败 500（不暴露路径）。

**测试结果**

- `tests/test_retrieval_stats.py` 26 passed；Audit/Report/Stats/Admin 定向回归 141 passed。
- 完整 `pytest`：909 passed / 1 failed。唯一失败为 `tests/test_ndjson_replica.py::test_admin_stats_renders_replica_health_fields`，由并行提交 `ab8436b`（Stats UI 重构，移除旧 “Replica Health” 文案）引入，与本 API 无关；本 API 未改动任何 `web/` 文件。

**性能（隔离合成保留日志，10 个文件，99.2 MB / 26 万事件）**

| 场景 | 请求耗时 p50 | 备注 |
|---|---|---|
| All / 90 天 | ≈ 1952 ms | 扫描全部保留文件 |
| 单 Namespace / 90 天 | ≈ 1905 ms | 扫描成本与窗口/命名空间无关 |
| All / 7 天 | ≈ 1882 ms | `available_from` 与全局关联需全量扫描 |

- 峰值内存（`tracemalloc`，All/90 天）≈ 119 MB，主要来自为“范围内非空搜索”保留结果 ID（合成含 5.0 万条）；真实保留规模下应显著更低。
- 本轮不引入缓存/预聚合。已知可选优化（留待后续评审）：仅当搜索被某条 report 引用时才保留其结果 ID，可将内存降至与反馈规模成正比；以及窗口远小于保留期时能否早停（当前因 `available_from`/全局关联不早停）。

**Review 修正（2026-10-10）**

- Namespace 现在作用于**全部搜索指标**：`total/successful/failed`、`modes`、`trend`、`non_empty_searches` 均限定在选定 Namespace（此前只有 `non_empty` 被限定，导致响应不自洽），`available_from` 与全局 `search_id` 关联仍与请求范围无关。
- 时区解析与 Namespace 存在性校验移入 `_run` 工作线程（不再阻塞事件循环，且经过运行期准入）；`invalid_timezone`/`timezone_database_unavailable`/`namespace_not_found`/`invalid_namespace` 仍由 handler 映射。
- 新增测试 `test_namespace_scopes_all_search_metrics`。

**未做**：不改 `/api/audit`、`/api/stats`、`/api/stats/metadata`、MCP 工具、审计写入格式；不接 Retrieval 前端；未提交、未重启生产服务。

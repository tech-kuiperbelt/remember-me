# Stats Metadata API Coding Plan

日期：2026-10-10  
状态：后端只读统计 API 已实施并通过测试；Stats 页面前端另行安排。  
依据：[STATS_API_DESIGN.md](../../design/STATS_API_DESIGN.md)。  
调查：[Stats 页面与统计 API 调查](53-stats-metadata-investigation.md)。

本计划仅覆盖后端只读统计 API；Stats 页面设计与实施另行安排。

## 1. 冻结接口与统计口径

新增 `GET /api/stats/metadata`，采用设计中的响应字段：

- `scope.namespace`、`total_memories`
- `namespace_options`、`default_namespace`、`namespace_distribution`
- `dimensions.categories/keywords/anchors`，各含 `unique_count`、`covered_memories`、`coverage_ratio`、`top`

确定以下行为：

- 省略 Namespace 表示 All；显式空串或纯空白返回 HTTP 400、`invalid_namespace`。
- 非空名称去除首尾空白，再使用现有格式规则校验。未知名称返回 HTTP 400、`namespace_not_found`，沿用现有错误结构。
- 重复 `namespace` 或不支持的查询参数返回 HTTP 400、`invalid_request`。
- `namespace_options` 始终包含全局存活 Namespace 和配置默认值，去重后按名称升序。
- `namespace_distribution` 仅描述当前范围，按数量降序、名称升序；合法但为空的默认 Namespace 返回空数组。
- 每维度 Top 固定最多 100 项，按数量降序、值升序；distinct 和 Coverage 使用完整范围计算。
- Category 不计零使用种子。Anchor 跨记忆统计保留现有大小写区别。
- 比例返回未做展示舍入的 0–1 数值；分母为零时返回 0。

旧 HTTP、MCP tool 和 resource 契约保持兼容。

## 2. Storage 聚合与一致快照

在 `MemoryStorage` 增加 `get_metadata_stats(namespace=None)`，SQLite 实现、Dual 直接委托 primary。

SQLite 使用现有连接、RLock 和显式 `SAVEPOINT metadata_stats`：

1. 首先查询全局存活 Namespace 及数量，建立读取快照。
2. 从该结果计算范围 total 和范围分布，同时保留全局 Namespace 候选供 Service 使用。
3. 对固定的三个 dimension 分别执行汇总查询和 Top 查询：汇总查询计算 `COUNT(DISTINCT iv.id)` 和 `COUNT(DISTINCT m.id)`；Top 查询按 `iv.value` 分组，计算不同 Memory 数并排序，`LIMIT 100`。
4. 全部查询连接现有关系表，并限制 `m.deleted=0` 和可选 Namespace。
5. 成功释放 savepoint；异常回滚到 savepoint 后释放，不提交或回滚调用者的外层事务。

无记忆范围直接返回零值和空列表。聚合结果读取完成后释放锁，Service 再计算比例和组装响应。

全局候选、范围分布和三维度统计来自同一个数据库快照。配置默认值来自当前不可变 Settings。此次不增加表、索引、缓存或独立数据库连接，也不读取正文、metadata JSON、embedding BLOB、FTS 或 NDJSON。

## 3. Service 与 Admin 接入

新增 `memory_metadata_stats(namespace=None)`：

- 在查询前检查显式 Namespace 的类型、非空和格式。
- 使用 Storage 同一快照返回的全局名称集合判断 Namespace 是否存在，再加入配置默认值作为合法候选。
- 未知名称抛出现有 `NamespaceNotFound`；避免先调用 `check_namespace()` 另查一次，再与统计快照产生时间差。
- 组装冻结后的公开响应，移除 Storage 内部辅助字段。
- 不调用 `memory_stats()`、`get_stats()` 或全量记录导出。

Admin 新增 handler，通过现有 `_run()` 执行 Service 方法，在路由表声明 `read` 策略并使用统一异常映射。更新路由完整性断言。

本期不修改 `stats.js`。现有初始化、全局刷新及分类重试仍通过旧 Stats 更新共享候选；新接口不接触 Namespace／Category 全局注册表。

## 4. 正确性与兼容验证

新增聚合与 API 定向测试，并扩展 SQLite／Dual 共用契约测试：

- 全局、单 Namespace、空数据库、空默认 Namespace 及未知 Namespace。
- 缺失或空 metadata、单条多值、字段清空、删除、历史孤立索引值。
- Category 零计数种子排除；Keyword 多值不重复计 Coverage。
- Anchor 单条内 ASCII 去重，以及不同记忆中的大小写值分别计数。
- Top 数量边界：0、4、5、29、30、99、100、超过 100；并列排序稳定，截断不影响 distinct 和 Coverage。
- Namespace URL 编码、中文、特殊字符、空白、保留名称、超长、重复及未知参数。
- SQLite／Dual 返回一致；用失败桩确认新路径不调用旧 Stats、副本检查或 embedding。
- 使用临时 WAL 数据库的第二连接，在统计查询之间提交修改，验证当前请求仍返回同一快照、下一请求看到变化；同时验证外层事务未被意外提交。
- 检查旧 `/api/stats`、Keyword API、MCP `stats`／`list_keywords` 和 `memories://stats` 的既有契约。

先运行新增测试和相关 Storage、Admin、Namespace、Anchor、Keyword、快照测试。后端抽象契约增加后运行完整 pytest，检查受影响的替身及集成路径。

## 5. 性能记录与交付

在隔离临时数据库准备 1 千、1 万、10 万条记忆，包含多 Namespace、倾斜分布和高基数 Keyword／Anchor。分别测全局、小 Namespace、大 Namespace：

- 保存聚合 SQL 的 `EXPLAIN QUERY PLAN`，记录索引使用和临时聚合／排序。
- 预热后重复测量，记录 SQL 聚合耗时、Service／HTTP 整体耗时的 p50、p95。
- 并发执行普通写入，记录写入延迟及存储锁等待；不接触生产数据库。
- 不预设延迟 SLA，不因出现扫描或临时排序就自动新增索引。若实测暴露问题，记录查询优化及索引建议，单独评审 schema 变更。

交付包括后端实现、测试结果、查询计划与性能记录，以及更新后的实施状态。

## 6. 实施记录与性能结果（2026-10-10）

已实施：`MemoryStorage.get_metadata_stats(namespace=None)`（`app/storage/base.py`）、SQLite 实现与 Dual 委托、`MemoryService.memory_metadata_stats`、Admin `GET /api/stats/metadata`（`read` 策略、统一异常映射）及 `ROUTE_TABLE`/`EXPECTED_ORDER` 更新。新增 `tests/test_stats_metadata.py`（27 例）；全量 `pytest` 884 passed。旧 `/api/stats`、Keyword、MCP `stats`/`list_keywords`、`memories://stats` 契约未改。

**发现的查询计划问题与查询策略修正（未改 schema、未加索引）：** 原始 `dimension`-first 的 Top 查询在带 `m.namespace=?` 时被 SQLite 翻转为 `index_values`-first 计划，大 Namespace 下退化为二次复杂度（10k 记忆、单维度 ≈ 4.1s）。改为“从 `memories`（经 `idx_memories_namespace` 收敛）→ `memory_index_values`（PK memory_id）→ `index_values`（rowid）”并 `MATERIALIZED` 成 `(value, memory_id)` 中间集后再汇总，同一数据降至 ≈ 4ms。summary 与 top 共用该 CTE。

**实测（隔离临时库，每 scope 预热后 20 次采样，SQL 聚合 p50/p95）：**

| 规模 | 全局 | 小 Namespace | 大 Namespace |
|---|---|---|---|
| 1k | 3.7 / 3.8 ms | 0.15 / 0.18 ms | 4.1 / 4.4 ms |
| 10k | 40.7 / 46.7 ms | 1.3 / 1.4 ms | 46.0 / 50.5 ms |
| 100k | 790 / 803 ms | 38.7 / 41.7 ms | 560 / 568 ms |

每次调用执行 4 条语句（1 条 Namespace 分布 + 3 维度 × [summary + top]）。查询计划均命中 `idx_memories_namespace`（scoped）或 `idx_memory_index_values_value`（global），代价为 `count(DISTINCT)`/`GROUP BY`/`ORDER BY` 的临时 B-tree；Top 的 `LIMIT 100` 不减少精确 distinct/coverage 所需的扫描。

**结论／后续建议：** 无需为本 API 新增 schema 索引；大 Namespace 或全局在 10 万级已达数百毫秒，属按需（非轮询）请求下可接受范围，无 SLA 预设。两点留待前端实施阶段与后续评审：① 全局 100k 的 790ms 若被证明影响交互，可评估“先用受限集合求 Top、再单独补 distinct/coverage”的两段式查询；② `MATERIALIZED` 中间集在超大 All 范围下会占用临时内存，规模化前需复测。需要索引或 schema 变更时单独评审，不随本 API 顺带引入。

## 目标与顺序

后续工作聚焦 UI，用户将逐项提出页面布局与功能组织的修改意见。路线提出时，前端集中在 `web/index.html`，页面结构与多个页面的状态、样式和交互混在一起。现已拆为 HTML、静态 CSS 和原生 ES Modules，入口为 `web/static/js/main.js`。

采用“先做一轮小范围重构，再逐项调整 UI，随需求逐步完善结构”的路线。
第一轮降低连续修改的成本；后续模块边界根据实际布局与交互需求调整，避免按旧页面
提前设计完整组件体系。

## 第一阶段：保持行为的小范围重构

范围：

- 分离 HTML、CSS 和 JavaScript，让页面结构、样式与交互代码各有明确入口。
- 提取公共能力：API 请求、错误提示、弹窗、格式化等。
- 按现有功能划分页面逻辑：记忆管理、搜索、关键词、配置与维护等。
- 明确各模块的状态归属，减少共享变量和跨模块直接操作 DOM。
- 梳理初始化、事件绑定与页面切换，避免重复注册和隐式调用关系。

约束：

- 保持现有界面、布局、功能和交互行为；本阶段以职责整理为目标。
- 保持后端 API 与业务语义，静态资源提供方式按拆分需要调整。
- 暂不引入前端框架、构建工具或复杂组件体系。
- 具体文件划分、模块依赖和事件迁移方式在实施前结合现有代码确定，本路线图
  不提前固定所有模块名称或目录。

验收：

- 从真实服务入口验证页面与拆出的静态资源正常加载。
- 使用现有隔离浏览器回归确认主要页面和交互行为；测试入口随资源拆分同步调整。
- 验证初始化、页面切换、弹窗、请求错误处理及必要的跨页面状态传递。
- 后端如涉及静态资源路由修改，运行对应路由回归。
- 无新增浏览器控制台错误，事件不重复绑定；核对模块状态与依赖是否清楚。

## 第二阶段：按用户意见逐项调整 UI

- 用户提出页面布局、导航、功能分区与交互修改意见。
- 每项修改先明确目标与影响范围，再在对应模块实施和验证。
- 新布局改变职责边界时同步调整模块；根据实际复用需求提取公共组件。
- 每次变更记录行为变化及验证结果，保持改动可独立 review。

## 第三阶段：布局稳定后的结构复核

主要页面与功能组织稳定后，检查剩余重复代码、状态耦合和交互一致性。
根据实际维护成本决定是否进一步组件化或引入框架，并说明收益和迁移成本。
进入本阶段不意味着必须采用框架或完成全面重写。
